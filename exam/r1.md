## 1. 推理引擎（vLLM / SGLang）算 Harness 吗？采样参数（temperature / top_p）算吗？为什么？

> **原始作答**：推理引擎不算 harness，我理解推理引擎是配套模型使用的。模型不是冷冰冰的权重，我理解模型应该是能够进行推理的 API，而这个是靠推理引擎实现的。采样参数我理解也不是 harness，因为也是和模型推理相关的参数。

**边界**：第一问答对了归属，但理由是循环论证——它把要证明的边界当成了前提。第二问判错了。真正缺的是一个可操作的判据：**用什么标准划分两个团队的边界**，而不是"它跟模型有关所以不归我"。另外漏了一层：即使不归你，它和你之间也有一份契约，契约破了成本会落在你这边。

## 2.「模型与 Harness 的共同进化」——举个具体例子

> **原始作答**：harness 的比如工具调用、指令遵循等设计，如果 harness 在这方面信任模型，校验方面不那么严格，就需要模型的 RL 等，提升模型这方面的能力来适配 harness。反过来，模型在比如长远规划问题上能力不行，就需要 harness 更多的定义逻辑和路径，类似最开始的 workflow。

**边界**：取舍方向摸对了，而且"类似最开始的 workflow"这句很准。缺的是再往下一层：**harness 的设计会进入训练分布**，于是补丁会被模型学走、固化、变得难删。答到"补丁会变成负债、行为变更必须和模型版本绑定发布"才算过。

## 3. 工程岗为什么点名 KV Cache？对应 Harness 里的哪个问题？

> **原始作答**：KV cache 我理解主要还是推理加速，减少 token 消耗方面，对应的主要是 harness 里的长上下文、记忆等问题。

**边界**：答的是它在推理侧有什么用，题目问的是它在 harness 侧要求你怎么写代码。缺的是一条**设计约束**——具体到"上下文的哪一部分必须保持字节稳定"，以及为了它要放弃哪些看起来更优雅的做法。这一问的判据是：能不能说出一条会让你的代码更丑、但必须这么写的规定。

## 4. Tool Use / MCP / Skill 分别在哪一层？边界在哪？

> **原始作答**：tool 在最底层，是模型的 FC 能力，有 FC 能力的模型才能适配中间的 MCP 层。MCP 屏蔽了不同工具来源的交互细节。skill 是最上层，最靠近应用层。边界在于 Tool Use 是模型内置能力，MCP 是标准协议，skill 属于上下文管理范围。

**边界**：相对位置大体对，是全场最好的一题。三处要修：Tool Use 只说了模型那一半，漏了宿主那一半（执行、超时、权限、把失败信息回灌给模型）；MCP 的关键价值不是"屏蔽细节"而是**复用**，这条在答第 6 题时提到了，第 4 题反而漏了；Skill 用"层"来比喻会带偏——它和 tool 不是上下层关系，是两个维度。

## 5.「对模型行为有品味有判断力」——你打算用哪个具体现象证明？

> **原始作答**：这种判断力来源于感觉，就好像觉得一个人好看，可以从鼻子、眼睛等角度来说，但是单拎出来并不好说明什么，组合在一起就是好看。模型的上下文窗口大小、指令遵循能力、长任务规划能力等等组合起来都比较好，我会觉得这个模型比较好。

**边界**：这一题答成了三种典型形状的组合——审美类比、维度清单、拿"感觉"当证据。它们共同的问题是**不可验证**。品味能拿出来的形式只有两个：**预测**（我预判它会在这一步坏，然后它真的坏了）和**干预**（我改了某处，它变好了）。维度清单谁都能背，不能当证据。

## 6. 研究员自己写脚本也能调模型，为什么需要统一的 Agent 接入与运行框架？

> **原始作答**：脚本很多地方是能够进行复用的，把这些能复用的地方组装起来就成了 Agent 运行框架，比如记忆管理、上下文管理、skill 接入、MCP 接入等等。

**边界**：复用是对的，但它是次要原因，而且 JD 自己已经写出来了。主要原因是另外三个：**实验可比、结果可复现、规模可承载**。顺序反了——先有"同一个模型在不同 harness 下分数差十个点，那这个分数就不算模型能力"，才有理由统一。

## 7. 第 4 条职责（不中断现有研究任务的前提下渐进式重构）为什么值得单列成一条？

> **原始作答**：我理解就是滚动发布，不要影响用户体验。

**边界**：答成了另一个问题。这里没有"用户"，服务对象是正在跑的训练任务；约束不是"不停机"，是**行为兼容**——旧脚本跑出来的结果必须还能跟历史对比。这是分水岭题，也是这份卷子里最值得重答的一题。
